## 1. 先选对同类文档

按“当前人工文档 → 本次指定样例 → 同类且较新的用户章节 → 下述参考”确定结构。结构选择与业务规则优先级分别处理；旧文档的格式仍可复用，旧规则不因此重新生效。

| 任务 | 样本结构 | 使用方式 |
|---|---|---|
| 修改现有 PRD | 当前标题、表格列名、编号、字段顺序、行边界 | 原位修改，三列不改两列，已有条目不改成统一模板。 |
| 月度需求合集／局部优化 | 已有的“序号／标题／云效”索引；功能主题标题；“原型／需求分析”两列或分级条目 | 有真实需求链接时保留索引；不为单项修改新建月度合集，不造云效链接。 |
| 完整模块改造 | 需求标题、调整记录、功能结构／流程、导航及功能按钮、列表表头、功能设计、关联功能优化 | 仅在当前文档或选定样例采用时沿用；功能设计可为“原型图／功能点／详细分析”三列。没有来源不补空流程图。 |
| 单个配置／表单模块 | 原型对应模块；基本／基础信息、明细、按钮、规则 | 按相近样例的实际顺序，新增、编辑、查看相同处合写，差异处单列。 |
| 接口／定时任务等规则 | 接口名称、请求参数、响应参数、字段校验、处理逻辑、关联改造；或触发、取数、处理 | 不为非页面规则虚构页面、原型或截图；已有单列“需求分析”表也应保留。 |

保留 `1.` → `a.` → `i.` 或原文已有的分级数字编号；导出的连续数字不等于原文层级，须结合缩进和所属段落还原。不要统一重排成一种编号。标题直接命名功能或改造点，例如“实际值明细支持批量修改”；不用“赋能”“全面提升”等口号。

## 2. 按用户的业务逻辑拆解

以下是检查思路，不要求每项生成一个章节：

1. **定位改哪里**：菜单路径、涉及页面、涉及功能；需要时简述当前场景及问题。不要从通用产品愿景起笔。
2. **先放回现有模型**：区分“原有不动／原逻辑”“新增”“更名”“去掉”“调整”。已有能力只写引用和真实差异。
3. **落到页面和字段**：说明新增位置、展示顺序、必填、单多选、枚举或来源、默认和可改；条件变化时补显示、隐藏、置灰及关联值处理，有依据才写。
4. **展开具体分支**：按业务对象、配置值、单据状态、组织或数据源分层写“若……则……”。不要用“自动匹配”“智能校验”跳过判断过程。
5. **把取数写成处理顺序**：触发 → 状态／范围过滤 → 组织、日期、科目等维度匹配 → 取哪个金额 → 去重、汇总或占用 → 结果及联动。适用环节写清优先取什么、取不到如何处理；不能将不同字段的顺序混成通用取数优先级。
6. **向相邻功能检查**：新增、编辑、查看、审批、查询／表头筛选、排序、导入、导出／自定义导出、接口、历史数据。只写受本次改动影响且有依据的项，不能把检查清单全部变成建设范围。
7. **用具体场景验证**：多组织、上下级、同一来源重复、空值、金额与周期、取消及失败等适用情形。先核对用户已写的特殊分支；缺口列待确认，不自动加审批、草稿、版本或重审。

业务背景只解释确实需要解释的动机。复杂取数可以详细展开，简单增加一个列表字段可以只有一两条。相同页面操作合并表述；多个页面的字段来源、可改性或状态限制有差异时才分别写。

## 3. 文字与句式

正文直接陈述字段和动作，多用“新增／增加／调整为／更名为／去除”“默认……，可改”“置灰不可修改”“若……，则……”“否则提示：‘……’”“同步调整”“其余逻辑同……”。

- 字段可以写为“字段名：必填，下拉框，单选，枚举……；默认为……，支持修改”，也可沿用当前句式；不机械追加类型、来源、精度等空项目。
- 当前模块以“字段名称／是否必填／数据类型／业务规则”等表格逐行说明字段时，继续使用该表格，保留“基本信息／合同／发票”等分组；不能强行改成冒号句。2026-01、2026-04需求均包含这类结构。
- 位置写为“‘××’字段下方新增……”“置于‘××’字段后”“列表最后一列新增……”。同名字段不同页面可改性不同，分别交代。
- 查询说明写“字段：连接符；控件／选项；是否排序”。字段较多时，沿用“字段名称／连接符／展示说明／设置字段排序”等原表头，不改成通用字段字典。
- 操作先写按钮何时亮起／置灰、单笔或批量，再写点击后的页面、结果和必要提示。提示语有来源时保留引号内原文及参数。
- 公式用业务字段名直接写，计算与展示的单位、时间、精度及空值规则有差异时简短补充。示例用于说明难点，不为每项机械编造示例。
- 状态和枚举保留原标签及已给定的编码，例如“0-收入；1-支出”；不得自行补编码或改名。
- 界面标签按原文使用【】或引号；说明使用短句、分号和括号。保留有效的备注和强调；不复制错字、空编号、人员提及、催办语气或导出乱码。

不将正文写成咨询报告。避免“为了确保系统的安全性与一致性”“提供统一且可追溯的全生命周期能力”“建议建立完善的……机制”等泛化长句。应直接写明哪个对象、什么条件、做什么、结果是什么。

## 4. 原文短例与迁移方式

以下仅为写法示例，业务规则只在对应原文成立；迁移时必须替换成目标任务已知规则。

**字段位置与默认值**，来自2026-06“外币预算剩余需求”：

> “预算模板”字段下方新增“预算币种”字段：必填，下拉框，单选，下拉枚举为所有币种

**条件、按钮、结果与联动**，来自2026-08“实际值明细支持批量修改”（保留原句）：

> 支持勾选多笔数据点击，未勾选数据时按钮置灰显示
>
> 仅支持勾选交易方向相同（同为收入/支出）的收入明细/支出明细数据点击批量修改，否则按钮置灰
>
> 点击后展示批量修改操作弹窗
>
> 修改后同步更新流水信息

**处理顺序**，来自2026-11“事后预算控制占用”（概括，不是逐字引文）：

1. 预算执行时触发。
2. 判断有效控制规则。
3. 按组织、日期、支付方式、科目、状态筛选单据。
4. 应付单及来源应付的付款单去重。
5. 剔除已存在占用记录的单据。
6. 剩余单据进行占用。

学习的是先筛选、再去重、再处理的拆解方法；不能将“仅占用不控制”套到其他业务。

**同一含义的表达校准**（示范改写，不是用户原文）：

- 不采用：“为提升用户操作效率，系统应提供批量维护能力，并确保上下游数据的一致性。”
- 采用：“列表左下角新增‘批量修改’按钮；未勾选数据时置灰。点击后打开批量修改弹窗，修改后同步更新关联流水。”

后者也只有在任务已确认按钮位置、弹窗和更新对象时才能写入正式 PRD。

## 5. 处理历史修订和未定内容

- 删除线、颜色、高亮、P0/P1、版本注记和“暂时不做／该版本不做”均应结合上下文判断。删除线可能表示取消、替换或完成，不能一律解释为已实现；不得把划掉的旧方案与新方案拼接为有效规则。
- 原文保留草案方案、问题、建议与详细需求时，区分讨论和最终规则。若哪项生效不明确，则列待确认；不把前文“方案1／方案2”当作两个都要建设。
- 月份、修改时间和主题重复仅用于定位，不足以证明覆盖关系；按具体条目核对。相同内容跨月结转，不重复统计为多项独立风格证据。
- 例如2026-11“控制维度优化”同时出现“未填写交易对手按科目控制”和“不进行控制校验”，不能合成一个默认分支；指出冲突，保留用户决定的优先级。
- 格式学习与业务判断分开：不能因照用户写法而保留矛盾，也不能因补齐业务而改成另一套表达。用其句式写已确认的纠正，未知内容放待确认。

## 6. 写完后双向对照

先以最接近的用户章节为参照，逐项检查：拆解顺序、章节和列名、行粒度、编号层级、字段顺序、术语、句式、详略、差异引用；再检查字段、操作、金额、异常及联动有无遗漏。

结构改了、长篇解释多了、简单改动写成完整方案、同类模块句式不同、遗漏用户特定分支，均须修正。内部对照不默认输出成额外章节、评分表或检查报告。没有用户对实际生成稿的反馈时，只能报告已完成技能与样稿核对，不能声称已经达到百分之百一致。

## 7. 保理人工稿对照后的校准

2026-10-30，对比[保理优化](https://alidocs.dingtalk.com/i/nodes/ydxXB52LJq7pexNrIM9NE9pGWqjMp697)第四章人工维护稿与第六章独立稿。独立稿按用户要求未读取第四章；新增的项目决定不能据此视为可提前获知。学习以下方法，不将本次金额口径、字段必填性或直联范围推广为通用业务政策。

- **页面内完整描述**：同一页面的基本信息、明细、组件、联动和按钮，优先放在同一行，按页面分组及原有编号展开；仅在实际为独立页面、流程或差异状态时拆行。不要将同一表单拆成多个通用规则章节。
- **先复用，再写差异**：确认现有组件可覆盖时，保留可定位的组件引用，展开本次新增或改变的行为，不重新定义组件内部规则。用户要求复制相邻章节对应表述时，直接复制并核对目标对象及差异；不能用“与第五章对应模块相同”代替正文。该要求不等于禁止“与提款中占用授信列表相同”等有效组件引用。
- **字段行为成组核对**：检查来源、默认值、可编辑性、联动、必填性之间是否一致，尤其是同名字段在不同页面的差异。不能自行将可选改为必填、置灰改为输入或将开户行等同融资机构；缺少规则时保持未定。
- **写清对象生成链路**：在所属页面写明来源单据 → 生成单据 → 后续处理对象及结果；只区分金额或强调“融资不等于收款”不能替代具体映射。识别原有单据与新生成单据的职责，不为补业务完整性额外引入台账或金额维度。
- **保留已确认操作，补齐实际影响**：用户明确允许特定状态下编辑或作废时，保留该操作，核对影响字段、关联单据、占用和计划，缺失处理列待确认；不能凭通用经验直接禁止，也不能声称其后续处理已明确。
- **覆盖检查不能被篇幅替代**：逐项核对卡片字段、抽屉筛选、金额口径、选项、按钮、移动端及实际受影响的接口，避免概念说明很长却漏掉已有功能。截图承担的内容未经辨读，不宣称已覆盖。
- **反馈分开归因**：区分风格偏差、独立生成时已知规则遗漏、后续新明确的业务决定，以及人工稿自身缺口。只沉淀可复用方法，不照抄错字、不完整条件或未经核实的矛盾。
